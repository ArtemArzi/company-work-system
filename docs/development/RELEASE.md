# Новая функция: из продукта в компанию

Маршрут для агента сопровождающего. Артём развивает общий продукт в его репозитории; компании получают изолированную основу с сохранением своих данных и местных решений. Внутренние документы разработки остаются здесь. Общий метод обновления, конфликтов и восстановления — [template-update](../../template/standards/template-update.md); точные команды компании — [runtime](../../template/standards/runtime.md).

## Выпустить общую основу

1. Пройти вход продукта по AGENTS и продолжить его PLAN/задачу. Новую общую функцию разместить в `template/`: код, метод, парный SKILL/YAML и ближайшая карта по необходимости. Использовать существующие механизмы. Данные клиентов и их настройки сохраняются у компаний.
2. Проверить полезный сценарий новой функции и затронутые ошибки, совместимость и карту. По поручению владельца каждый завершённый выпуск, включая инструменты выпуска, получает версию в `template/release.yaml.version` и короткую строку в истории корневого README. Номер относится к выпуску, а не к каждому промежуточному коммиту. README показывает историю; единственный источник номера — release.yaml. Сохранить результат и конкретные ограничения в существующей задаче; выполнить соразмерную независимую проверку по AGENTS.
3. Закоммитить точные проверенные файлы продукта. Из чистого состояния собрать переносимый выпуск одной командой; `VERSION` заменить фактической версией основы:

```sh
python3 scripts/product.py .local/release-candidate.git --bundle .local/company-work-system-VERSION.bundle
```

Команда использует прежний subtree split и общую проверку всей достижимой release-only истории, затем создаёт и проверяет Git bundle. Выход содержит SHA выпуска, путь и SHA-256 пакета. Существующий пакет, включая повреждённую символьную ссылку, не перезаписывается. В Git продукта сохранить разрешённый результат обычным push/readback по AGENTS. Повторные проверки ради закрывающей заметки не нужны.

4. Передать клиенту проверенный bundle и его hashes по разрешённому каналу либо подключить отдельно разрешённый release-only remote. Push исходников в product main сам по себе не устанавливает функцию компаниям. Прямой clone/fetch истории product main в компанию нарушает границу: там есть разработка и её внутренние документы. GitHub Releases, новый внешний репозиторий и массовая рассылка этим маршрутом автоматически не создаются.

## Применить выпуск к выбранной компании

Агент компании получает разрешённый пакет, проверяет его hash и историю, сверяет установленный предок в `.system/base.json` и готовит чистый актуальный экземпляр от общего Git компании по её существующему порядку. Незавершённые чужие изменения сохраняются. Для обычной компании из шаблона:

```sh
git clone --bare /absolute/path/company-work-system-VERSION.bundle .local/received-release-VERSION.git
python3 scripts/system.py update .local/received-release-VERSION.git .local/update-VERSION
```

Каталоги должны быть новыми. `update` ещё не меняет общий репозиторий компании: результат — отдельный `verified-candidate`, `conflict`, `needs-reconciliation` либо `already-installed`. Работа и настройки `company/` и `work/` сохраняются. Конфликт и старые активные привязки разбираются в сохранённом кандидате, затем используется штатный `finish-update`; приёмку спорного смысла merge не заменяет.

Проверенный кандидат доставить тем же `deliver` в действующий общий remote компании с `--expected-base` из результата update. Запускать CLI самого кандидата, чтобы проверки использовали полученный код. Получить remote readback. Следующий самостоятельный вход сотрудников получает обновление из общего Git компании. Не доставлять кандидат обновления в product remote.

**Work имеет свой owned Git:** сначала его штатный `prepare`, затем `update` и `deliver` по `company/WORKFLOW.md` самого Work. Обычный корневой Git Work принадлежит сайту. Work-local маршрут используется только в этом рабочем пространстве и не входит в шаблон клиента.

## Если функция требует местной настройки

Файл новой программы, навыка или общего стандарта может приехать обычным выпуском. Новые поля компании, источники, права, определения, лимиты и данные требуют отдельной принятой адаптации: выпуск не может назначить их за владельца или автоматически переписать `company/` и `work/`. Отключённые возможности остаются отключёнными до действующей настройки. Новые методы связать с ближайшими картами; исправить потребителей при переносе. Прежние гарантии и одно действующее местное правило сохраняются.

Проверка этого маршрута: тест `test_portable_feature_release_updates_client_without_development_or_data_loss` передаёт новый синтетический навык и программу через bundle в отдельную компанию, сохраняет настройки и работу, доставляет через общий Git, проверяет повтор и исключает историю разработки. Это локальная проверка; доступ к аккаунтам клиентов, native загрузка навыка и его бизнес-эффект проверяются отдельно при действительных полномочиях.
