## Принятый способ и этапы

1. На синтетических Git-компаниях зафиксировать baseline: одинаковые деревья/commits, 1/20/100 commits, повтор, маленькая правка, крупный blob, merge и два клиента. Раздельно измерять local validation, history, Git plumbing, fetch/push/readback. Для каждого сценария 1 раз прогрев и 20 измерений: median/p95, Git subprocess count, прочитанные bytes, количество commits/path entries/blobs. Указывать оборудование/версии/размер. Сеть не оптимизировать сокращением обязательной сверки remote. Данные только учебные, без провайдеров/платных вызовов.
2. Общий переносимый history checker внутри template/scripts, вызываемый существующей delivery и lifecycle.release_isolated/package/proposal границами. Профиль release сохраняет точный структурный allowlist и все refs; company export использует собственную policy. Общий traversal не сливает их полномочия. Company export policy остаётся company-owned: явные разрешённые пути, классы, baseline и точные исключения. Work hardcoded BASE/allowlist не становятся общими бизнес-правами. Область, выбранный Git source и полномочия определяются существующим контрактом компании; при отсутствии необходимой policy публикация защищаемых данных blocked, обычная локальная работа доступна. До интеграции описать policy schema/default и миграцию существующих учебных компаний; публичность remote не считается согласием на данные.
3. Первый вариант ускорения: проверенный Git context и snapshot policy один раз на ограниченную операцию; binary git cat-file --batch по exact object IDs с разбором размера; повторно используемые результаты проверки неизменных объектов внутри процесса. Проверять все пути/режимы каждого публикуемого достижимого дерева и все новые достижимые commits относительно доказанного разрешённого baseline. Dedup contents по blob ID не заменяет path-policy на каждом пути. На первое внедрение не использовать постоянный cache как разрешение пропустить проверку. Rev-list --objects без полного учёта путей и только diff HEAD не подходят.
4. Перед commit/push сверять policy fingerprint, repository identity, candidate HEAD и состояние индекса/целевой ветки; изменение инвалидирует расчёт, повтор или bounded остановка. Нельзя публиковать чужие staged bytes. Foreign ancestry, shallow/missing objects, replace/graft/alternate object stores и неподтверждённый baseline не получают исключение: нормализовать доказанную область либо blocked. Не использовать textconv/filters/follow-symlinks для проверки исходных bytes.
5. Вместо all-method bindings — явная dependency closure выбранной операции, recipe, результата, профиля, источников и местных методов. Обязательное ядро проверки/прав/identity и input hashes остаются. Списки зависимостей объявляются у канонических методов; операции динамического выбора источника добавляют выбранную specification. Не извлекать зависимости из свободного текста задачи. Неописанные пользовательские методы/динамические зависимости получают консервативный полный набор. Добавление/удаление/переименование зависимостей и изменение самого manifest проверяются, а не только старые файлы. Общая структурная проверка карты/ссылок сохраняется.
6. Config разделять на проверяемые выбранные facets только после явного описания их состава: identity, права/лимиты, активные local bindings, выбранные source/adapters и операция. ### История и policy

Один scripts/history.py даёт immutable Git context, byte-safe tree traversal и cat-file batch reader. Все файлы каждого достижимого commit tree проверяются по каждому path/mode, содержимое dedup по object ID, без постоянного разрешающего cache. Release policy структурная: прежний точный roots allowlist, отдельное исключение guide, допустимы только канонические relative skill projections; новый hooks root и точные native projection files добавляются лишь с реализацией. Все refs release/bundle учитываются, refs на не-commit объекты отвергаются; annotated tags должны завершаться commit. Новый alias ранее встреченного blob не пропускается. Release guard сохраняет прежние guarantees и дополнительно доказывает каждый путь; его ускорение не сравнивается с более слабым старым guard как эквивалентный workload.

Company export policy — optional company/config.yaml.export: schema_version=1, approved_by равен company owner, files (точные относительные пути), roots (явно разрешённые каталоги), binary_suffixes (явный список), baseline (null или full SHA выбранной разрешённой основы). Нет policy: существующая доставка в локальный common Git сохраняется как legacy local-only, без заявления проверенного external export; external delivery требует policy и прежних permissions.external_delivery/remotes одновременно. Policy не устанавливается автоматически, никаких Work allowlists/бизнес-лимитов. .local, private, runtime и env secret files не экспортируются; известные credential markers проверяются потоково, binary suffix не отменяет secret scan. Baseline задаётся явно approved owner, требуется ancestor всех разрешённых новых commits; точные baseline path/mode/blob могут переиспользоваться как разрешённое содержимое, но не дают разрешение новому пути. Null baseline — полная проверка. Любая missing/shallow/replace/graft/alternates ambiguity blocked; no implicit baseline from arbitrary HEAD/cache. Company refs scope — exact публикуемый commit и ancestors; bundle/release — все refs. Approval является явно записанным решением компании, не создаётся guard-ом.

Commit с активной export policy проверяет разрешённые working paths/content и уже имеющуюся историю до изменения индекса; staged tree проверяется тем же traversal перед commit. Чужие staged bytes не включаются; при отказе не reset/clean, файлы и чужие изменения сохраняются. Deliver независимо проверяет точный candidate commit после fetch и до push; policy/repository/HEAD/index fingerprints сверяются перед изменением, stale состояние stopped, push ordinary FF и readback прежние. Exact SHA делает объект неизменным; pending local bytes не становятся проверенным exported result. Новый механический guard не является доказательством полной обезличенности: обратный proposal требует прежнего exact owner approval и отдельного sanitized package.

### Зависимости и историческая совместимость

task.schema_version остаётся 1, task.bindings остаётся flat path→SHA map для старых readers. Новый additive binding_scope version1 содержит selection (skill, harness или common, selected source IDs), snapshot hashes config facets и release format facets; его hash фиксируется у task и evidence. New intake выбирает канонический recipe по известному acceptance.kind либо explicit --skill/--harness/--source-id. Ни свободный request, ни host memory не выбирают метод. Recipe объявляет dependency_paths, включает свои SKILL/YAML и standards, recursive skill steps и всегда общий core/operations/validation/dependencies/task-validation kernel. Недекларированная/custom/неоднозначная source closure — legacy полный набор. Отсутствующий declared dependency отвергается, не маскируется fallback. Изменение manifest, множества путей или selected file hash invalidates scope.

Config facets: schema/id/owner/permissions общие всегда; bindings по фактическим операциям выбранного recipe плюс intake/execute/context; sources только explicitly selected specs (для metrics unknown/ambiguous selection — full fallback); decisions для marketing; features/proactive/knowledge только выбранной операции; profiles и adapter files только явно выбранной среды. Поля вне описанного selection сохраняются консервативно при неизвестном методе. Config whole-file и release.yaml SHA остаются flat bindings для исторического compatibility; новый reader сравнивает selected facets, старый reader консервативно сравнивает полные bytes. Release semantics pin state_format/workflow_format и поддерживаемый binding_scope format, не unrelated release version.

Конфигурация для scope/admission читается одним stable byte snapshot: parsed YAML, полный hash и facets вычисляются из тех же bytes. Для выбранных sources scope сохраняет accepted specification snapshot с hash соответствующего facet; admission.specification должен совпасть с проекцией именно этого snapshot по общим source contract fields, одного ID недостаточно. Перед сохранением успешного evidence повторно подтвердить scope/dependencies и отсутствие изменения config snapshot; при изменении verified не сохраняется, предыдущие evidence/result остаются в истории, changed config не откатывается и зависимая операция blocked. Исторический metrics validator проверяет связь admission с сохранённым source snapshot/facet и временем независимо от актуального config; legacy evidence использует прежний whole-config admission контракт. config.export — live publication safety policy: каждый commit/deliver получает её независимый обязательный fingerprint, сопоставляет его с exact candidate config и повторно сверяет перед действием, даже если задача не выбирала skill deliver. Scoped deliver recipe дополнительно pin-ит export facet, но это не заменяет live guard.

Перед execute все scoped dependencies повторно проверяются; metrics admitted source ID должен принадлежать выбранным specs (legacy full fallback допускает прежнюю текущую admission проверку). Full company/config hash в evidence обновляется только при новом успешном verify после доказательства неизменности facets и связывается с фактическим source_admission.config_sha256/time; это не изменение старого evidence. Old evidence без binding_scope проходит прежнюю полную проверку, никогда silently narrowed. Scoped evidence carries exact same scope/hash as task, file bindings, config/time admission и criterion hashes. Исторический delivered result проверяется по сохранённой specification/time; unrelated current config не подменяет историю. Result source hashes и strict envelopes остаются независимо обязательными, даже если источник не был input intake.

Resume только existing owner/revision decision: архивировать previous verification/bindings/scope и явно пересобрать новый scope, без подделки старого PASS. Context/execute/tick/validation/update/finish-update/method-impact вызывают общий changed_bindings со scope. Rollback к старому reader сохраняет flat bindings/config evidence и получает консервативную проверку; новые поля не превращаются в silent weakened old verification. Обратный update/restore сохраняет данные; mismatched current scope блокирует только dependent active/waiting/blocked task, delivered evidence остаётся historical.
