## Наблюдение и первое неверное допущение

В template/scripts/core.py:method_bindings каждая задача закрепляет все .md/.yaml/.py в standards, skills, workflows, scripts, adapters, company/standards, всю company/config.yaml и release.yaml, а также входы. Это не фактическая зависимость конкретной операции. Изменение README другого профиля возвращается в changed_bindings; добавление нового файла само по себе этой функцией не обнаруживается. Полная проверка структуры выполняется отдельно и должна сохраниться.

[evidence/bindings-baseline.json](evidence/bindings-baseline.json): 20 запусков на временной чистой копии, 48 файлов, около 176 КБ, median 5.679 мс, p95 5.859 мс. Это воспроизведение широты привязок и локальный замер функции, не доказательство медленного синка. Исправление пока не предпринималось.

В продукте уже есть отдельный структурный release_isolated guard (lifecycle.py:13–23): rev-list --objects --all и allowlist путей выпускного bare repo. Он не равен полному company history/content scanner. При унификации использовать общий traversal и разные явно принятые policy профили для release/package/proposal/company delivery; текущий release guard не удалять до доказанной эквивалентности и проверки всех path aliases/refs.

Исторический export scanner находится в местном Work scripts/export_policy.py:history, не в главном template. У него полный ls-tree на каждый новый commit, повторные чтения policy и определение owned Git, отдельный cat-file процесс на blob. Work delivery вызывает scanner при подготовке и доставке. Это кандидаты причин задержки; wall-clock сравнение ещё не выполнено. Старые длительности полного suite не являются baseline синка. Work прочитан как источник механизма; его частные данные, policy и история не копируются в продукт.

Затронутый путь продукта: core.method_bindings/changed_bindings → operations.intake/decide/execute/context/tick → validation.task и metrics source_admission → lifecycle.update/finish_update → delivery.commit/deliver. Общий history scanner надо добавить в этот путь, сохранив один механизм доставки.

## Принятый способ и этапы

1. На синтетических Git-компаниях зафиксировать baseline: одинаковые деревья/commits, 1/20/100 commits, повтор, маленькая правка, крупный blob, merge и два клиента. Раздельно измерять local validation, history, Git plumbing, fetch/push/readback. Для каждого сценария 1 раз прогрев и 20 измерений: median/p95, Git subprocess count, прочитанные bytes, количество commits/path entries/blobs. Указывать оборудование/версии/размер. Сеть не оптимизировать сокращением обязательной сверки remote. Данные только учебные, без провайдеров/платных вызовов.
2. Общий переносимый history checker внутри template/scripts, вызываемый существующей delivery и lifecycle.release_isolated/package/proposal границами. Профиль release сохраняет точный структурный allowlist и все refs; company export использует собственную policy. Общий traversal не сливает их полномочия. Company export policy остаётся company-owned: явные разрешённые пути, классы, baseline и точные исключения. Work hardcoded BASE/allowlist не становятся общими бизнес-правами. Область, выбранный Git source и полномочия определяются существующим контрактом компании; при отсутствии необходимой policy публикация защищаемых данных blocked, обычная локальная работа доступна. До интеграции описать policy schema/default и миграцию существующих учебных компаний; публичность remote не считается согласием на данные.
3. Первый вариант ускорения: проверенный Git context и snapshot policy один раз на ограниченную операцию; binary git cat-file --batch по exact object IDs с разбором размера; повторно используемые результаты проверки неизменных объектов внутри процесса. Проверять все пути/режимы каждого публикуемого достижимого дерева и все новые достижимые commits относительно доказанного разрешённого baseline. Dedup contents по blob ID не заменяет path-policy на каждом пути. На первое внедрение не использовать постоянный cache как разрешение пропустить проверку. Rev-list --objects без полного учёта путей и только diff HEAD не подходят.
4. Перед commit/push сверять policy fingerprint, repository identity, candidate HEAD и состояние индекса/целевой ветки; изменение инвалидирует расчёт, повтор или bounded остановка. Нельзя публиковать чужие staged bytes. Foreign ancestry, shallow/missing objects, replace/graft/alternate object stores и неподтверждённый baseline не получают исключение: нормализовать доказанную область либо blocked. Не использовать textconv/filters/follow-symlinks для проверки исходных bytes.
5. Вместо all-method bindings — явная dependency closure выбранной операции, recipe, результата, профиля, источников и местных методов. Обязательное ядро проверки/прав/identity и input hashes остаются. Списки зависимостей объявляются у канонических методов; операции динамического выбора источника добавляют выбранную specification. Не извлекать зависимости из свободного текста задачи. Неописанные пользовательские методы/динамические зависимости получают консервативный полный набор. Добавление/удаление/переименование зависимостей и изменение самого manifest проверяются, а не только старые файлы. Общая структурная проверка карты/ссылок сохраняется.
6. Config разделять на проверяемые выбранные facets только после явного описания их состава: identity, права/лимиты, активные local bindings, выбранные source/adapters и операция. Whole-file company/config.yaml hash сохранять отдельно в историческом source_admission: нынешний validation.task требует его равенства evidence.bindings config hash. Нельзя просто удалить это поле. Для нового формата отделить исторический admission от текущих task dependencies и доказать соответствие выбранной принятой specification. Старые task schema/evidence читаются без переинтерпретации; сужение допускается только через явное resume/reconcile с сохранением истории и повторной проверкой. Перед кодом закрепить совместимую схему, при несовместимости — штатную миграцию/версию, не тихую смену schema 1.
7. Сравнить baseline и максимум три технических варианта на том же workload; бюджет первой серии 30 минут, один subprocess не дольше 60 секунд. Если данных не хватает, записать конкретный следующий эксперимент вместо бесконечных повторов. Это предел эксперимента, не лимит бизнеса. Выбирать вариант лишь при неизменной корректности и воспроизводимом выигрыше: median/p95 history ниже baseline, subprocess/повторные чтения меньше; простая задача не получает существенной регрессии. Численный целевой коэффициент назначить после baseline и сохранить до сравнения; не обещать ускорение заранее. Привязки принимать прежде всего по правильному invalidation, а не миллисекундам.

## Обязательные отрицательные случаи

- Секрет удалён из HEAD, но есть в публикуемой истории; тот же blob под запрещённым путём; merge чужой истории; неправильный baseline; дополнительные достижимые refs при экспортировании bundle/release.
- Symlink/submodule/mode/type, path traversal и пути с newline/NUL framing, бинарные/слишком большие объекты, отсутствующий объект, прерванный batch, concurrent policy/HEAD/index change и подменённая среда Git. Отказ сохраняет исходные файлы/индекс и конкретное объяснение.
- Несвязанная документация/другой harness/другая source specification не требуют перевыполнения задачи; выбранный standard/code/input/source/rights/local method требуют. Неисправная общая карта всё ещё отвергается общей структурной проверкой.
- Старые active/waiting/blocked/verified/delivered задачи, исторический metrics admission, source ambiguity, independent receipt и cancel сохраняют свои контракты; update/rollback и новая сессия используют ту же closure.
