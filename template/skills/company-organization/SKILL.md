# Организация компании

Метод — [system-evolution](../../standards/system-evolution.md), технические границы — [runtime](../../standards/runtime.md). Парный [workflow.yaml](workflow.yaml) задаёт вход, зависимости и остановку. Канонический корень определяется по `company/config.yaml`; в проекции ссылки разрешаются от `skills/company-organization`.

## Когда применять

Применять, когда документы, самостоятельные сущности, карты или ссылки могли разойтись: появился второй статус, файл оказался не у владельца, маршрут потерян, перенос оставил потребителей или нужно разложить уже существующие материалы. Не запускать ради косметической перестановки и не считать сигнал хука доказательством ошибки.

Сначала найти текущего владельца через `context`, ближайшую карту и поиск. Затем передать точный список затронутых путей в JSON-массиве команде `organization-check --paths-file <file> [--task <id>]`. Команда только читает и возвращает:

- место и тип каждого пути;
- обязательную и ближайшую карту;
- битые и входящие Markdown-ссылки;
- YAML/JSON-потребителей;
- исторические `task.json`, закрепляющие путь;
- полноту покрытия и hashes фактически затронутых bytes.

Неполное покрытие, alias, неизвестный владелец, смысловая неоднозначность или историческое закрепление означают `leave-open`: байты не двигать и решение не выдумывать. Обычный документ не получает автоматический «правильный каталог» только по имени.

## Решение и изменение

Для каждого пути явно выбрать одно: `keep`, `merge`, `move`, `link`, `create`, `leave-open`.

- `keep` — владелец и маршрут уже верны;
- `merge` — один владелец поглощает смысл, происхождение сохраняется, дубликат удаляется только после проверки потребителей;
- `move` — исправляются все найденные карты, Markdown-ссылки и структурированные потребители;
- `link` — добавляется только маршрут из существующей карты, второй статус не создаётся;
- `create` — допустимо лишь когда поиск подтвердил отсутствие владельца;
- `leave-open` — сохраняет исходные bytes и фиксирует вопрос владельцу.

Для изменения нужна принятая owning task. Сохранить первоначальный отчёт как неизменяемый `work/<id>/inputs/organization-snapshot.json` и указать только его во входах задачи; живые целевые файлы и карты относятся к output scope, а не к immutable inputs. Непосредственно перед каждой записью сверить ожидаемый preimage. После записи снова выполнить `organization-check`, сохранить ожидаемый postimage и повторить команду с `--expect <postimage>`: любое конкурентное изменение блокирует продолжение.

Не переписывать старые receipts, hashes, task inputs, `Result.sources`, evidence, source admission или history. Если перенос/слияние/удаление касается пути, закреплённого другой или исторической задачей, оставить путь либо создать совместимый маршрут; автоматическая правка истории запрещена.

Хуки `entity-before-write`, `entity-after-write` и `method-impact` остаются только локальными сигналами. Они не вызывают этот навык, не перемещают файлы и не расширяют права. После разрешённого изменения выполнить `validate`, затем общий commit/deliver. Повтор того же прохода должен вернуть отсутствие новых структурных изменений.

Простой аудит заканчивается отчётом без task/execute. Сохраняемое изменение проходит intake с explicit `--skill company-organization`, Result/critical через execute и доставку по общему Git-пути. Техническая проверка не доказывает, что организация удобна людям: применение подтверждается отдельно.
