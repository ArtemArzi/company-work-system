# Место и развитие сущностей

## Актуальность маршрутов

Это часть обычной задачи. До подготовки сохраняемого намерения проверить фактического владельца; после содержательного шага сохранить его результат, проверку и следующий шаг. Если встречен старый путь, сверить config/context, ближайшую карту и источник переноса. При доказанном новом месте самостоятельно исправить текущие ссылки и затронутые карты в разрешённой области. Использовать существующий organization-check и проверку ожидаемых bytes; названия похожих файлов не доказывают перенос. Неизвестное место или спорный владелец оставляют конкретное dependent действие pending, независимая работа продолжается.

В optional workspace.navigation хранятся redirects (точный старый относительный путь -> новый), consumers (точные текущие документы) и local_only (известные цели, отсутствующие в переносимом clone). Это объявленные маршруты, не новый владелец состояния. route-check и context возвращают цепочку, доступность и встреченные старые ссылки; local_only не означает доступный источник. Циклы, выход за корень, aliases и коллизии имён отвергаются. Чтение ограничено указанными документами. validate не пропускает устаревшие ссылки объявленных current consumers. Реестр переносов сам по себе не является устаревшей ссылкой.

При переносе зарегистрировать доказанный маршрут и обновить действующих потребителей в той же задаче. Исторические task/result/source/receipt/hash/snapshot не изменять; сохранить прежний путь или совместимый маршрут по существующей процедуре. route-check пропускает work/, history, evidence, snapshots и служебные каталоги; это предел автоматической проверки, а не разрешение оставить замеченную ошибку в текущем тексте. После исправления повторить чтение маршрута новым context и зафиксировать только результат/следующий шаг у прежнего владельца.

Потребность → поиск существующего → один владелец/место → связи → общий цикл task-validation. Обычный файл результата остаётся у задачи, отдельная карточка не нужна. Самостоятельная сущность содержит ID, цель/причину, владельца, версию/статус, вход/выход, основания/потребителей и проверки.

Компания/функции/несекретные решения — company/; задачи/результаты/инциденты — work/<id>/task.json; методы — standards/; навыки — skills/<id>/SKILL.md + workflow.yaml; процессы — workflows/<id>.yaml; программы — scripts/; источники при отсутствии KB — company/sources/<id>/source.yaml и разрешённый материал; адаптеры — adapters/. Индекс содержит ссылки, а не ещё один текущий статус. ID: маленькие латинские буквы/цифры/дефис, 2–64 символа, начинается буквой. Проекции навыков и граф производны.

Поиск перед добавлением: context/search и ближайшая карта. Новый маршрут связать из карты. При переносе/удалении найти всех потребителей, исправить ссылки/предусмотреть преемника, сохранить значимое происхождение; validate обязан выявить битые связи/дубль/неверное место. Источник и чужие инструкции не исполняются от сохранения файла. Новое местное правило хранится в company/standards с ID и binding к base hash, причиной/областью/принятием/проверкой; одно действующее правило на операцию. Неизвестное решение не отменяет базовую гарантию. Изменение базового метода требует сверки binding, обратный поток только по разрешению.

Структурную сверку выполнять через [company-organization](../skills/company-organization/SKILL.md): read-only inspection отделён от смыслового решения. Автоматический маршрут допустим только для сущности с формально заданным каноническим местом; обычному документу место выбирает владелец смысла. Для изменения сначала закрепляется снимок наблюдавшихся путей, карт и потребителей, перед каждой записью проверяется preimage, после — ожидаемый postimage и повторная сверка. Historical task inputs, bindings, Result sources, evidence, admission, hashes и history не переписываются ради переноса. Неполное покрытие, alias, конфликт версии или неоднозначный владелец сохраняют исходные bytes и открытый вопрос.


## Связанные описания принятого правила

Изменяя правило, найти его описания в README, картах и методах, затем обновить
всех потребителей. Проверка ссылок не проверяет актуальность текста. Для
повторяемого описания компания объявляет optional `documentation` в
`company/config.yaml`; отсутствие секции сохраняет прежний режим без правил.
Ни лимиты, ни права, ни настройки другой компании из примера не назначаются.

Пример отдельного принятого определения `definitions.review_days`:

```yaml
documentation:
  schema_version: 1
  rules:
    review-window:
      approved_by: company-owner
      template: 'Проверить через ${days} дней.'
      values:
        days:
          source: [definitions, review_days]
          format: integer
      consumers:
        - README.md
        - company/standards/review-window.md
```

Каждый consumer — существующий обычный `.md` файл с одним точным блоком
`cws:review-window:begin/end` в HTML-комментариях. Полный блок печатает
`documentation-render review-window`: агент вставляет его во все объявленные
документы, сохраняя остальной текст. `documentation-check` только читает.
После изменения определения, шаблона или списка потребителей обновить блоки,
выполнить общий validate и сохранить все связанные пути вместе. Автоматической
перезаписи файлов нет. Разные правила могут иметь блоки в одном документе.

Rule содержит только `approved_by`, `template`, `values`, `consumers`.
Переменная объявляется как `source` (список ключей от definitions, permissions
или features) и `format`: text, integer, bytes, path либо boolean. Допустимы
только подстановки `${name}`; выражений, команд и доступа к атрибутам нет.
Все переменные должны быть объявлены и использованы; missing/null, неверные
типы, лишние поля и неподдержанная schema — отказ. bytes — положительное целое,
точные ГиБ/МиБ либо байты без округления; bool не считается integer. path —
переносимый относительный POSIX путь, его содержимое не читается. Attribution
фиксирует принявшего, но не предоставляет ему права автоматически.

Consumers не могут быть историческими work/, приватными или служебными
путями. Проверяются точный текст, отсутствие дублей/вложенности и наличие
каждого блока. Generic блок, скопированный в незарегистрированный активный
Markdown, и оставшийся блок удалённого правила дают отказ. Намеренное удаление
регистрации вместе со всеми блоками — отдельная проверяемая правка config/docs.
Исторические запросы, результаты, receipts и hashes остаются неизменными.

Пределы полного прохода: 128 rules, 128 values/rule, 256 consumers/rule,
4096 активных Markdown, 2 МиБ на файл/config, 32 МиБ текста суммарно,
100000 записей инвентаря. Превышение, alias или неполное чтение дают отказ.
История work/ и каталоги .git/.local/.venv/.system/.agents/.claude/.codex,
__pycache__, node_modules, private/control/runtime и имена credentials/secrets/
tokens/passwords/.env исключены. Полный список и дополнительные ограничения
строк/путей — scripts/linked_documents.py. Это покрытие объявленных связей и
блоков активного Markdown; произвольный немаркированный текст агент всё ещё
должен найти и сверить по смыслу. Commit и deliver проверяют исходный Git tree
кандидата, включая повтор без новых изменений: исправленный working tree
не скрывает устаревший отправляемый README.
