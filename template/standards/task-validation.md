# Выполнение и проверка

В начале самостоятельной задачи или возобновления после перерыва: один preflight → перечитать AGENTS/методы после обновления → context/фактический владелец состояния → общий цикл ниже. Самостоятельная задача имеет отдельный ожидаемый результат; уточнение, промежуточный ответ, исправление или переход между навыками в рамках этого результата не начинает новый входной проход. Повторный fetch нужен при явном запросе свежего общего состояния, признаке чужого изменения/конфликта или возобновлении после перерыва. Иначе ответ опирается на версию, полученную в начале задачи, без обещания её свежести на текущую секунду. Шаг preflight внутри вложенного рецепта использует уже выполненный вход этой задачи; YAML не требует повторного вызова на каждом шаге.

Preflight использует принятый общий remote компании, проверяет identity и remote SHA; чистую отстающую копию обновляет только fast-forward, clean local-ahead показывает как pending delivery. При dirty/staged/untracked, незавершённом merge/rebase, detached HEAD, расхождении историй или недоступной общей версии зависимые действия остановить. Чужую работу не auto-commit/stash/reset, изменения не force-push. Нужное самостоятельное действие допускается в явно выбранном отдельном prepare-кандидате; первоначальная незавершённая работа остаётся на месте.

Человеку не поручать обычные fetch/commit/deliver: агент выполняет разрешённые шаги. Обращаться к человеку только за недостающим правом/смыслом или разрешением конфликта. При offline допустим явно обозначенный ответ по local SHA без заявления свежести; общие записи/доставка и решения, требующие свежих данных, ждут связи. После законченного результата — проверка/commit точных разрешённых paths → общий deliver/readback. Свежесть перед отправкой проверяет сама доставка; отдельный preflight непосредственно перед ней не нужен. Успешный readback закрывает доставку: не повторять sync, fetch, запрос GitHub API или приёмку неизменённого кандидата ради финального ответа. Вопрос без файловых изменений не требует коммита/отправки. Локальные промежуточные коммиты допустимы; отправка — по завершении задачи или явному запросу передать промежуточный результат. Локально сохранённое не считать общим. Фоновые hooks/таймеры этим правилом не включаются.

Размер проверки выбирать по смыслу и последствиям, а не числу строк. Мелкая правка — опечатка, рабочая ссылка, оформление или узкое уточнение с полностью понятным эффектом, без изменения бизнес-правил, поведения программы, полномочий, состава публикуемых данных или формата состояния. Автор читает итоговый diff и проверяет затронутую ссылку/формат; отдельный агент, новый журнал и полный тестовый набор не нужны. Применимость сам агент определяет кратко, без отдельного интервью.

Для документа с многими связанными изменениями, расчётами или противоречивыми источниками уместен один независимый block review итогового документа. Для небольшого изменения кода — затронутые проверки и один result review, когда его требует host policy; без полной пары приёмок. Сложная архитектура или существенный риск данных/прав/денег/внешнего состояния требуют независимой приёмки плана и результата по действующей политике. Сохранять установленный independent_required у уже принятой задачи; автор его не снимает ради ускорения.

Приёмка относится к содержательному результату. Обычные итоговые заметки и запись полученного verdict не открывают её заново. Поправки проверяет прежний reviewer только в затронутой области. Если изменились смысл, зависимости или риски, повторить соответствующую проверку. Не добавлять проверяющих по одному на каждый файл, коммит или sync. Полный regression выполнять при изменении общего механизма/контракта или перед выпуском кода, а не после каждого текстового исправления.

Область: законченная содержательная операция. Зачем: уверенность автора и текст PASS не являются проверкой. Метод: актуальный контекст → исходный запрос/критерии/версии → разрешённое действие → точные проверки → критический проход → ограниченное исправление → сохранение → свежая общая версия/доставка/чтение. Единственный цикл; другие стандарты добавляют только свои условия.

Перед действием зафиксировать владельца, ожидаемый выход, неизвестное и входы. Результат обязан иметь первичные основания, период/единицы при расчёте, полноту, ограничения и следующий шаг получателя. Формат, данные и поведение проверяет одна библиотека scripts/validation.py; смысл требует конкретных ссылок, контрпримера и сопоставления с запросом. Семантический критик остаётся свидетельством автора, не независимой гарантией. При материальном риске/сложности требуется отдельная независимая приёмка exact candidate.

task.json содержит hashes входов, стандарта, программы, результата и критического прохода. Изменение зависимости отменяет прежний допуск; неизменённое не перепроверять без требования свежести. Известный плохой пример обязан отвергаться. Не менять принятую acceptance или валидатор ради PASS. Записать сбой и первое неверное допущение, проверить существующий способ, исправить затронутое, повторить проблемный случай. Две попытки без новых фактов останавливают подход.

Verified означает локальную проверку указанного результата. Доставка, применение и эффект отдельны; unknown не равно нулю. Неразрешённое действие/спорный смысл адресовать владельцу. Внешний timeout означает неизвестный исход: readback до повтора; общий CLI внешних записей не делает. Местный способ допускается при прежнем контракте. Изменение этого стандарта — выпуск сопровождающего через template-update.

Точные зависимости берутся из declared recipe closure и выбранных config facets
по [runtime](runtime.md). Сохраняется совместимый flat bindings и historical
source admission; legacy не сужается автоматически. Общая структура/карты
проверяются независимо от scope. Хуки используют эту библиотеку, работают
локально и не запускают синк, LLM, ревью или полный suite на каждой записи.
